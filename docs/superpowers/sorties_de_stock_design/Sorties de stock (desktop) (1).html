# Handoff : Sorties de stock (consommé / jeté / retiré) ## Overview Cette feature permet à l'utilisateur de **faire sortir un article du stock** (frigo, garde‑manger…) en indiquant **ce qu'il en a fait** : `Consommé`, `Jeté`, ou `Retiré`. Chaque sortie : - décrémente la quantité de l'article (ou le supprime si la quantité tombe à 0), - écrit une **entrée de journal** (`log`) horodatée et attribuée à un utilisateur, - est **annulable pendant 10 secondes** via un toast. La feature inclut aussi des **suggestions proactives** : quand des articles sont périmés depuis plus de 3 jours, l'app propose de confirmer ce qu'on en a fait (mangé / jeté / ignorer), pour garder le stock et les statistiques anti‑gaspillage justes. Deux surfaces sont fournies : **mobile** et **desktop**. Même modèle de données, même logique métier, interactions adaptées à chaque plateforme. ## About the Design Files Les fichiers de ce dossier sont des **références de design réalisées en HTML/CSS/JS vanilla** — des prototypes qui montrent l'apparence et le comportement souhaités, **pas du code de production à copier tel quel**. La tâche est de **recréer ces designs dans l'environnement existant de l'app Fresh / MonFrigo** (React / React Native / Vue / SwiftUI / etc.) en utilisant ses patterns, ses composants et sa librairie d'icônes déjà en place. Si aucun environnement n'existe encore, choisir le framework le plus adapté au projet. Points d'attention spécifiques au projet Fresh : - **Aucun emoji** dans l'UI (règle projet). Utiliser exclusivement des **icônes Lucide**. - Réutiliser les **tokens de couleur et la typo de la charte Fresh** déjà définis dans le codebase plutôt que de redéclarer les valeurs ci‑dessous — les hex listés ici servent de référence/fallback. ## Fidelity **Haute fidélité (hifi).** Couleurs, typographie, espacements, rayons et interactions sont finaux. Recréer l'UI au pixel près avec les composants existants du codebase. Les seules libertés attendues concernent l'adaptation aux conventions du codebase (nommage, structure de composants, gestion d'état). --- ## Modèle de données ```ts type StockItem = { id: string; name: string; category: { label: string; icon: LucideIcon; colorKey: string }; // ex. "Produits laitiers" storage: string; // "Réfrigérateur", "Garde-manger", "Congélateur"… qty: number; // quantité en stock unit: string; // "yaourts", "portions", "L", "pot"… detail?: string; // précision optionnelle, ex. "2,75 L" addedBy: string; // "vous", "Sarah"… addedOn: string; // date d'ajout status: | { type: 'fresh' } | { type: 'expiring'; days: number } // expire dans N jours | { type: 'expired'; days: number }; // périmé depuis N jours }; type StockExitLog = { itemId: string; qty: number; // quantité sortie action: 'consumed' | 'wasted' | 'removed'; user: string; at: string; // ISO timestamp }; ``` ### Les 3 actions de sortie | Code | Libellé FR | Sens | Icône Lucide | |---|---|---|---| | `consumed` | Consommé | Mangé, cuisiné, utilisé | `utensils` | | `wasted` | Jeté | Périmé, avarié, plus envie | `trash-2` | | `removed` | Retiré | Donné, transféré, erreur de saisie | `package-x` | La distinction `consumed` vs `wasted` est le cœur métier : elle alimente les **statistiques anti‑gaspillage**. `removed` est une sortie neutre (ni consommé ni gaspillé). --- ## Logique métier (commune mobile + desktop) ### `doAction(itemId, action, qtyOut)` 1. Borne `qtyOut` entre 1 et `item.qty`. 2. Prend un **snapshot** de l'article (pour l'undo). 3. Pousse une entrée dans `logs` (`StockExitLog`). 4. `remaining = item.qty - qtyOut` : - si `remaining <= 0` → **retirer l'article de la liste** (animation de sortie ~330 ms, puis re‑render). - sinon → `item.qty = remaining`, re‑render. 5. Affiche un **toast d'annulation** (10 s). ### `undo(snapshot)` Retire la dernière entrée de `logs`, restaure l'article (quantité et position) et re‑render. Déclenché par le bouton « Annuler » du toast ou à l'expiration… non : **uniquement** si l'utilisateur clique « Annuler » avant la fin du compte à rebours. À l'expiration des 10 s, l'action devient définitive (le toast disparaît, aucun appel undo). > Dans une vraie app : `doAction` doit idéalement **différer l'appel réseau de 10 s** (optimistic UI) ou écrire immédiatement puis proposer une mutation de compensation à l'undo. Choisir selon l'architecture existante. ### Suggestions (péremption) - `suggestItems = items` filtrés sur `status.type === 'expired' && status.days >= 3 && !ignored`. - **0 article** → pas de bannière, badge cloche masqué. - **1 article** → bannière au singulier avec 3 boutons : `Oui, jeté` (wasted), `Non, mangé` (consumed), `Ignorer`. - **≥2 articles** → bannière groupée « N articles périmés… » + bouton « Faire le point » qui déplie une liste ; chaque ligne a Jeté / Mangé / Ignorer. - Une action depuis une suggestion s'applique sur la **quantité totale** de l'article (`qtyOut = item.qty`). - `Ignorer` ajoute l'id à un set `ignored` (masque la suggestion sans toucher au stock). - Le **badge rouge de la cloche** (topbar/nav) affiche le nombre de suggestions actives. --- ## Écrans / Vues ### 1. Transitions clés : `doAction` (mutation + log + toast), `undo` (restauration), `ignore` (filtre suggestions). Toutes déclenchent un re‑render de la liste **et** de la bannière de suggestion. --- ## Design Tokens (charte Fresh — référence) > Réutiliser les tokens existants du codebase.
